# Mingle — first implementation contract

Product: Mingle (formerly Relay). This is a durable first foundation for the multi-month product described in vision.md. Build an original local workspace with real persistence and supported provider harnesses. Describe implementation and deployment evidence separately; the distributed stage below remains opt-in and requires cloud/device acceptance validation.

## Stack

pnpm workspace; React 19 + TypeScript + Vite; Tailwind or plain CSS with design tokens; TanStack Router and Zustand if useful; Node >=24.13; WebSockets; SQLite via node:sqlite; node-pty; Monaco and xterm; Electron desktop entry point. Effect may be used where useful, without copying T3 abstractions. Core architecture matches T3's UI / Node / provider process separation. Rust isn't required to launch the Codex Rust executable.

## Desktop distribution

Mingle is intended to be an installed desktop application. Linux x86-64 packaging stages Electron, a checksum-pinned official Node runtime, the compiled backend, production dependencies and built web assets. The installed app manages its loopback server and stores data under the Electron user-data directory, without requiring pnpm, a source checkout or a manually started server. Provider CLIs and their logins remain separately installed.

`pnpm package:linux` produces the standalone archive; `pnpm package:arch` adds an installable `.pkg.tar.zst` and checksum using `makepkg` as an ordinary user. `pnpm package:deb` creates a Debian amd64 package on Debian/Ubuntu. Linux packages install a launcher, icon and properly owned sandbox helper. `pnpm package:windows` builds a Windows x64 per-user installer on a native Windows runner. Package creation does not install into the host or publish a release. The Linux workflow verifies installation only inside its disposable runner. AUR/GitHub Release publication requires the owner's approval; there is no AUR entry or automatic updater yet. See desktop-distribution.md for the exact build/publication contract and outstanding release prerequisites.

## HTTP and WebSocket contract

All HTTP routes use /api. Errors: {error: string}. JSON success bodies, except file content endpoint. API server port 4310 on 127.0.0.1, Vite port 5173. Vite proxies /api and /ws. Production server serves apps/web/dist. New source checkouts default to .mingle under the repository root; existing .relay data is reused in place. MINGLE_DATA_DIR overrides this choice, with RELAY_DATA_DIR accepted as a legacy alias. Both state directories remain untracked.

- GET /api/bootstrap -> Bootstrap (shared contracts), includes durable messages, events, run records and structured tool calls. Runs retain start/end times and monotonic elapsed duration; tool lifecycle updates reuse a stable provider ID per run. Bootstrap prioritizes active runs and bounds recent run/tool records, with tool output tails capped at 2,000 characters. GET /api/runs/:id/tools loads up to 1,000 full bounded records; GET /api/tool-calls/:id loads one detailed record. Both reject archived sessions. Tool output is bounded at 20,000 characters and exposes outputTruncated when clipped. Initial state creates one clearly labeled example project with a local folder, readme/contract files, tasks and TWO idle sample sessions (not active provider calls). isExample=true. Do not invent metrics or completed runs. Runtime defaults to this example until user opens their own project.
- POST /api/projects {name,path} -> Project. Path must exist; use canonical real path. PATCH /api/projects/:id {name} -> Project changes its display name without moving its folder. GET /api/projects/:id/files?path=relative -> FileEntry[]. GET /api/projects/:id/file?path=relative&sessionId=optional -> {content,path}; PUT same endpoint {content} saves text. Refuse traversal, symlink escapes, .git and secrets. Files can be scoped to a session worktree.
- Open Project has New project, Local folder and Git URL sources. GET /api/directories lists native directories from home or an absolute/tilde path, supports bounded filtering and last-segment completion, and returns native parent/home/root locations. Partial paths cannot select their parent. POST /api/directories/reveal opens the system file manager. POST /api/projects/new creates a fresh child folder, initializes Git and makes an empty initial commit using configured identity; POST /api/projects/clone clones an HTTPS/SSH URL into a fresh child. Existing destinations reject, failures keep the reserved folder with a recovery message, and no push or dependency installation occurs. Paths preserve spaces and native separators; Windows drive/UNC paths and macOS/Linux roots are resolved by the server. See project-picker.md for bounds, authentication and platform verification limits.
- POST /api/sessions CreateSession -> Session. Only projectId is required; omitted name/provider/model/effort/policy/isolation resolve from application defaults, with an automatic session name. Git projects isolated by default using unique worktree+branch under data directory. Clear errors for nonrepo/unborn HEAD. Nonisolated sessions explicitly opt in. PATCH /api/sessions/:id {name?,provider?,model?,effort?,policy?,pinned?,unread?} -> Session. Pin/unread flags persist independently of conversation activity and do not change updatedAt. Metadata-only flag changes broadcast state without adding activity events. Run settings reject changes during an active run or cleanup; a provider change rejects after a provider conversation exists, while model/effort changes preserve that conversation. DELETE /api/sessions/:id archives a standalone session from Mingle, stopping an active provider run and session-scoped terminal before archival, then disconnecting its browser; conversation history and metadata remain, and project files, worktrees and branches are never removed. Group-member sessions reject this route so the user can delete the whole group or remove the agent from its roster. POST /api/sessions/:id/messages SendMessage -> {accepted:true}; starts asynchronous provider run. 409 if active. POST /api/sessions/:id/interrupt -> {ok:true} cancels process, denies pending approvals.
- GET /api/projects/:id/git?sessionId=optional -> GitStatus. Read-only status and diff. The separate repository control API described below adds explicit commit, push, branch and pull request actions.
- POST /api/tasks CreateTask -> Task. PATCH /api/tasks/:id UpdateTask -> Task; reject cycles, cross-project deps or ownership, invalid transitions past unfinished deps. Mark downstream ready when dependencies done. POST /api/tasks/:id/run -> {accepted:true}; dispatch assigned session with task context, moves to review on successful turn, never auto-done.
- POST /api/handoffs Handoff -> WorkspaceEvent. Verify source/target same project, artifact committed at revision in source repo; create compact reference and durable receiving system message. Does not silently merge or start a paid model run. Include artifact content or source path reference for consumption; downstream session should receive it with next explicit run.
- POST /api/approvals/:id {decision:'approved'|'denied'} -> Approval. Approvals belong only to active local run; expire/deny on restart and interruption.
- PATCH /api/settings UpdateSettings -> AppSettings. No credential UI or secret storage; Claude uses its existing local CLI login or an explicit ANTHROPIC_API_KEY in the server environment. Executable paths may be configured. GET /api/providers -> ProviderInfo[]. POST /api/providers/refresh -> ProviderInfo[]. Accurate diagnostics; codex --version and Claude executable selection/auth-status probes with timeout. Installed != authenticated; do not claim authentication based on executable alone.

`DELETE /api/projects/:id` removes the project from Mingle's visible workspace without deleting its folder, worktrees, branches, conversations, tasks or attachments. Migration 9 adds `projects.archived_at`. Project-scoped reads, bootstrap and group routing hide removed projects; running native work/cleanup, dispatched group work, terminals and repository mutations prevent removal. Pending group scheduling is paused transactionally. Explicitly reopening the same canonical folder (or importing an existing native conversation there) restores the project and history; team scheduling requires an explicit resume. The project picker and Project settings provide the same confirmation dialog explaining retained files.

Each provider card in Settings exposes its saved executable path alongside the resolved path, a Save path action and automatic detection. Explicit paths are authoritative in existing runtime discovery. Changes from another window or managed installation update an untouched draft while preserving a local edit in progress. Saving a path reruns availability diagnostics without starting inference. Provider credentials remain outside Mingle settings. See [Provider paths and project removal](workspace-settings.md) for the user flow and restoration behavior.
- GET /api/events?after=integer&projectId=optional -> WorkspaceEvent[] for replay.
- WS /ws -> ServerEvent. Connected client receives state.changed on mutation. Client re-fetches bootstrap (debounced), session.delta updates live text at its absolute offset to handle snapshot overlap. Terminal messages use shared ClientEvent with {type:'terminal.ready',terminalId} server handshake and {type:'terminal.error',message} for failed starts. PTY owner socket only, project/session cwd validation, kill on disconnect. No shell interpolation.

## Provider module contract

apps/server/src/providers/index.ts exports createAdapter(provider: Provider): AgentAdapter and detectProviders(settings: AppSettings): Promise<ProviderInfo[]>; interface types in @mingle/contracts. Provider agent owns only this subtree + provider tests and docs/provider-research.md.

Codex: launch codex app-server over stdio; JSON-RPC initialize/initialized; thread/start or thread/resume; turn/start; deltas and tool records; forward approval requests to host callback; interrupt/abort; process timeout and cleanup; restore provider session id. No OAuth extraction. Use existing CLI login.

Claude: use official @anthropic-ai/claude-agent-sdk query(), resume provider session id, stream partial text, map canUseTool to requestApproval, support AbortSignal. For this local workspace, let Claude Code use the local user's existing login; an explicit API key takes precedence. Probe login status through `claude auth status --json`, never by reading credentials. Do not implement an OAuth broker, token extraction or browser credential storage. Honor model and effort. No automatic fallback model substitutions. See provider-research.md for the dated authentication sources and hosted-product scope.

Antigravity: use Google's official ACP executable and sibling local harness over JSON-RPC, independently of the interactive `agy` CLI. Initialize-only background discovery must not start OAuth. Explicit Settings sign-in invokes the runtime's own Google authentication and creates a metadata session without submitting inference. Run-scoped MCP servers use ACP session setup; permissions return through `session/request_permission`. Resume provider conversation IDs without silently starting a replacement conversation. Model and thinking controls come from native config options; `default` / `none` preserve native selection. Unsupported native history import, selected skills, custom compaction thresholds and unreported usage fields stay explicit. See provider-antigravity.md.

Antigravity catalog refresh uses `POST /api/providers/antigravity/auth { refresh: true }` and the existing asynchronous status/cancel endpoints. It reads native models, per-model reasoning choices and asynchronous slash commands without a model prompt; if credentials require a browser, it aborts and requests explicit sign-in. A validated public metadata cache survives restarts for up to seven days, scoped to executable fingerprint and native account configuration, without retaining authentication state, credentials or login links. Native default model controls expose the actual reported model name and reasoning options. Missing command metadata can be discovered by a session catalog request without starting paid inference.

OpenCode: the fourth independent provider uses the user's `opencode acp` executable over stdio. Optional `opencodeExecutable` and `defaultOpencodeModel` settings preserve old settings compatibility. Native models use provider/model IDs; per-model variants become reasoning efforts, including the native default. Metadata discovery and project slash-command discovery submit no model prompt. Each run owns its child, isolated loopback listener, permission rules and HTTP MCP capabilities; credentials remain under OpenCode's control. Resume failures never create a replacement conversation. Queued metadata probes have cancellation/deadlines and are drained on shutdown; run locks remain held until child closure. Native history import, quota, selected `$` skills, custom compaction thresholds, nonstandard tiers and Auto review remain explicitly unsupported. See provider-opencode.md for researched protocol behavior and validation limits.

`GET /api/providers/antigravity/install` returns `AntigravityInstallState`; explicit `POST {}` starts a bounded asynchronous download of pinned Google ACP 1.4.1 archives. Both executable and harness are extracted to a private version directory outside tracked source, checked by archive SHA-256 and per-entry CRC, and published together. Settings polls status and refreshes diagnostics after completion. Linux/macOS/Windows x64/ARM64 archives have recorded local digest pins; those are Mingle pins rather than Google signatures. A newer user-selected executable path is preserved if it changes during installation. Managed runtime downloads are separate from the desktop package and need no Python installation.

`GET /api/providers/antigravity/auth` returns the current explicit login job status and optional `phase` (`starting`, `waiting-for-browser`, `loading-models`). Only the active browser-waiting phase can contain an ephemeral, validated native Google `authorizationUrl`; `browserError` reports host-launch failures without its URL. `POST {}` starts Google's bounded browser flow; Mingle launches its native link through the host default browser and Settings offers an external-link fallback. `DELETE` cancels that flow without signing out. Credentials and authorization URLs are not persisted by Mingle. Server shutdown cancels installation and authentication and waits for cleanup before closing SQLite.

## Run and tool activity

Provider adapters emit `tool.activity` lifecycle snapshots keyed by the provider invocation ID and `tool.output` deltas. A start/result pair updates one invocation and counts once. Only real provider parent IDs produce nested calls; shell command strings are not parsed to invent process trees. Provider-reported command, working directory, process ID, exit code, result and timing are retained when available. Text is redacted before persistence/transport using the existing best-effort credential scrubber.

The runtime persists run records and message/run links with additive schema migration 3. Run elapsed duration uses a monotonic host clock during normal completion/interruption. Recovery marks unfinished runs/tools interrupted without fabricating an elapsed duration across server downtime. Old text-only history is retained without guessed identities, timings or subprocesses.

Migration 5 adds a saved change summary and bounded patch to each run. Before invoking the provider, Mingle captures eligible tracked/untracked working files into local Git objects; after the provider stops, it compares the two trees. This includes staged, unstaged and committed edits without modifying the real index, refs, working files or creating commits. Ignored untracked and denied secret paths are excluded, and no clean filters, external diff helpers or textconv commands run. The result describes net workspace changes, including concurrent edits by other writers. Nonisolated sessions include a shared-folder notice.

`SessionRun.changes` carries the summary in bootstrap; `GET /api/runs/:id/changes` loads the saved patch on demand. The endpoint rejects active runs and archived/missing sessions, and reports historical runs without snapshots as unavailable rather than reconstructing their edits. The UI places one card after each finished run's final assistant message, with compressed folder groups, aggregate/per-file counts, binary indicators and a read-only diff dialog. Empty known snapshots are hidden.

Capture is bounded to 2,000 eligible files, 10 MiB per file, 100 MiB total and a checked 15-second budget (individual Git operations also have timeouts). Incomplete/unreadable/unstable snapshots or unsupported submodules make the summary unavailable, preserving provider execution. Summary lists cap at 200 files with complete overall totals; saved patches cap at 500 KiB, and the viewer limits each file to 1,500 rendered lines with a notice. Renames are represented as deletion/addition. Capture baselines live in memory, so interrupted runs recovered after a server crash have no reconstructed summary. Completed summaries and patches remain in SQLite. Git objects written for checkpoints are unreferenced and follow the repository's normal garbage collection.

## Native plans and interactive questions

`POST /api/sessions/:id/messages` accepts `intent: 'plan'` only when the provider adapter has a real native read-only plan mode. Providers report proposals through `session.plan`; Mingle stores them as durable plans associated with the generating run. Plans are editable, ordered revisions with explicit dependency edges. Self, missing, duplicate and cyclic dependencies reject. Editing resets approval; only the exact current revision can be approved or executed. Execution is an explicit user action and runs through the session lock. Group plan intent requires exactly one selected agent, rejects native commands/skills, withholds browser/team side-effect tools, and persists through the durable group delivery queue. Model prose never schedules other agents.

Plan execution retains the original request's selected context references and attachments. Session plans validate that references remain scoped to the session; group plans resolve references and attachment ownership from the original group request and target the same active member. If the source request is unavailable or no longer valid, execution rejects and asks for a new plan rather than dropping context silently.

Native provider questions are durable, run-scoped records. `requestUserInput` suspends its provider run and exposes `POST /api/questions/:id/answer` and `/cancel`; answers must cover exactly the active fields and obey each field's option/multi-select rules. Secret-marked answers are passed to the waiting provider but excluded from persisted answers. Questions are cancelled on explicit cancellation, timeout, run interruption or server restart; stale answers cannot resume another run.

The shared additive schema sequence preserves the existing migration slots: 13 ensures project/group archival columns, 14 creates session plans and user questions, 15 remains reserved for the shared mentions work, 16 adds group request plan intent/execution identity, 17 repairs branch-order variants idempotently, and 18 adds session/group message context-reference columns. These guards support databases that reached v16 with plans/questions and group metadata in either order. Project archival was also introduced earlier in the integration sequence; v13 reconciles both archival columns. No provider inference is part of migration or automatic checks.

## Provider controls and command discovery

### Local conversation import

`/import` opens a local history picker for Codex and Claude Code, also accessible from the command palette and project menu. `GET /api/imports?provider=codex|claude&projectId=optional&cursor=optional` lists native conversations in pages. The optional project filter uses the project's server-resolved folder. `GET /api/imports/:provider/:id` reads metadata and a bounded public-text preview. `POST /api/imports {provider,conversationId}` imports and opens a conversation without starting inference. The ID and original folder are resolved again from native metadata; clients cannot supply a replacement folder.

New imported sessions retain the provider conversation ID and use its existing canonical directory directly, with Supervised permissions, Standard service tier, and a supported inherited effort. A reported model is retained when present in the current provider model catalog; otherwise the saved provider model is used with a notice. The next explicit composer send resumes the native conversation through the existing adapter. Import does not create a worktree, replay the transcript into a prompt, change branches, copy credentials, inherit old permission grants, or run a model automatically. Missing folders and filesystem roots reject.

Repeated imports reuse the existing Mingle session, restoring archived metadata on explicit selection, without duplicating messages or resetting its settings. An existing session in a different folder or running in Mingle rejects. Native APIs do not reliably establish whether another CLI process is using the conversation: finish an active CLI run before continuing in Mingle. Provider-native resume failures remain visible; Mingle never silently starts a replacement conversation.

Imported history contains bounded public user/assistant text with credential-shaped strings scrubbed; tool output, reasoning and attachments are not reconstructed. Native context remains with the provider. Historical tool counts, timings, token totals and changed-file snapshots are not invented. Preview/import limits and missing metadata are disclosed. Discovery/read requests are coalesced while pending and limited to four distinct concurrent requests, without a persistent transcript cache.

Additive migration 4 stores `sessions.service_tier`, defaulting existing sessions to `standard`. CreateSession, UpdateSession and settings accept a service tier. Provider model metadata carries supported reasoning identifiers, model aliases, speed tiers, reported defaults and model-specific permission modes. Session creation/model changes normalize inherited defaults to supported choices; explicit unsupported effort, tier or permission values reject. Active runs and provider cleanup keep configuration locked.

`GET /api/sessions/:id/catalog` returns native commands, skills and bounded discovery notices, cached briefly; `?refresh=true` requests a refresh. Discovery uses Codex `skills/list` or Claude SDK initialization/control methods with an open prompt stream that yields no messages. It starts no inference. `POST /api/sessions/:id/messages` also accepts optional `skills: string[]`; IDs are resolved against a fresh server-side catalog and session identity is checked again before starting the run. Arbitrary client-supplied skill paths are never trusted. Claude accepts one explicit skill selection per message.

`GET /api/sessions/:id/usage` returns `SessionUsage`: native provider quota windows, optional credit/reset details, bounded notices, fetch time and current local conversation totals. `?refresh=true` bypasses the normal 60-second cache after a minimum 15-second cooldown from the previous result. Unavailable snapshots cache for 15 seconds; concurrent reads coalesce. Snapshots stay in bounded process memory. The route rechecks session existence and provider/model identity after asynchronous discovery. Codex reads `account/rateLimits/read`; Claude uses its experimental SDK usage control with transcript scanning skipped. Both have bounded requests and process cleanup without starting inference. `/usage` is a local composer action and remains available during a run. Its dialog shows only reported values; no reset redemption, invented credit denomination, inferred replenishment date or account credential access is implemented.

Codex Auto selects its native approval reviewer; Full access uses the native unrestricted sandbox and no approval prompts. Claude maps to its native `auto` and `bypassPermissions` modes; Auto is shown only for models reporting support. Codex Standard explicitly sends `serviceTierForTurn: 'default'`; Claude speed maps to the SDK flag-settings `fastMode`, with runtime availability failures surfaced. Existing CLI authentication remains provider-owned. See provider-feature-parity.md and the dated provider controls research documents for exact mappings and limitations.

## Chat attachments and targeted native actions

Migration 10 adds attachment metadata, message links and a durable native invocation on group messages. Binary contents live outside source in the private runtime directory. Bootstrap and message history carry metadata and opaque IDs, never attachment bytes or base64.

- `GET /api/sessions/:id/attachments` and `GET /api/groups/:id/attachments` restore unsent uploads for that conversation. `POST` on the same paths streams a single raw file; its percent-encoded display name is supplied through `X-Mingle-Filename`.
- `GET` or `HEAD /api/attachments/:id/content` serves a validated raster preview; `?download=true` requests a download. Other file types always download with an opaque MIME type and restrictive content headers. SVG and HTML never render inline. `DELETE /api/attachments/:id` discards an unsent upload; sent files belong to retained history.
- Session and group message schemas accept `attachmentIds` and allow a message containing files without text. Scope ownership, draft status, counts and size limits are checked again when linking files transactionally to the accepted message. Uploads and reads reject archived sessions and removed projects.

Limits are ten files and 50 MiB total per message, at most 10 MiB per raster image or 25 MiB per other file. Claude's native inline image limit lowers its image cap to 5 MiB. Streaming uploads enforce these limits independently of declared Content-Length. Failed uploads are cleaned up; abandoned unsent files expire after 24 hours. Run staging uses verified, read-only copies outside the repository, retained while provider cleanup holds its run lock. Generic file pointers do not claim to decode arbitrary binary formats or bypass the selected permission policy.

Claude images use the official SDK's structured user-message stream. Codex images use native `localImage` input items. Antigravity and OpenCode use ACP image blocks only when their runtime advertises image input; other files use resource links with explicit native paths. Codex input modalities come from its model catalog; ACP transport capabilities come from initialization, while Claude's transport capability describes its documented SDK content API. Unreported model capabilities remain unreported. OpenCode's native command route takes text arguments and drops nontext inputs, so slash commands with attachments reject before a model turn.

`GET /api/groups/:id/members/:memberId/catalog` returns the active member's native task commands, supported skills, limits and discovery notices without inference. Human group messages may carry one `invocation` containing its catalog identity, arguments and recipient. Settings controls and Mingle commands are excluded from native task menus. Native actions always target one active member; provider aliases must be unambiguous. Configuration remains in member settings.

Group invocations retain the intended member, native session, provider and model. Dispatch revalidates the current catalog and resolves skill paths server-side, with membership, queue and settings checks after asynchronous discovery. A queued action cannot silently become a different agent's command. Claude preserves leading slash syntax and appends dynamic team context through its SDK preset with `snapshot: false`. ACP carries context after the native command using embedded content; Codex receives an explicit native skill input with separate text context. No extra setup inference turn is submitted.

## UI direction

Minimal desktop workspace, responsive down to 900px (smaller widths graceful overlay). Neutral black/charcoal surfaces, white emphasis and rare blue accents; no purple. Sidebar contains project/session selection, search and compact creation actions; secondary task/activity/map views are under the footer's More menu. Conversation is primary; context pane and terminal start closed and can be opened on demand. User messages use right-aligned soft bubbles; assistant messages are plain prose without provider icons or repeated model headers. Composer has editable model, effort and approval controls using shared polished choice popovers. New Session creates directly without a popup, using stored provider/model/effort/workspace defaults. Settings is a full page with General, Project, Providers and Appearance categories, not a drawer. Session rows offer a grouped context menu via right-click, Shift+F10 or a three-dot button. It supports pin/unpin, rename, manual read/unread flags, copy details, project settings and confirmed deletion. Pinned sessions appear first; opening a session explicitly clears its unread flag. Project settings edits the display name and shows the canonical folder path; new-session defaults remain global. Keep truthful example identification, accessible controls and visible failures. Preserve file editing, diffs, tasks, handoffs and real terminal functionality. A compact activity disclosure appears per run, with a live elapsed timer, authoritative tool/category counts and a final duration. Expanding reveals structured tool details and supported child calls; full bounded output loads on demand. Legacy adjacent tool messages group as output records, with descriptive command previews and no invented invocation count. See ui-direction.md for references and the current revision. Original code, no T3 source copy.

Workers must commit their own scoped changes, with no coauthor trailers, and never push. Orchestrator owns root packages/config/contracts/docs except provider-research.md. Workers may create their app package.json. Coordinate dependency additions in final report; root owns shared lockfile.

## Shared Chromium browser and context compaction

The server owns `BrowserService` separately from provider runtimes and the UI. Managed sessions launch persistent Chromium profiles under the ignored runtime data directory, with the Chromium sandbox enabled. Existing-browser sessions attach only after explicit human consent to a selected detected browser's local debugging metadata or a validated loopback CDP endpoint. Discovery checks directory/metadata existence without opening credential files. Existing logins and open web tabs remain in the running browser; disconnect detaches without closing it. No cookie extraction, password decryption or profile copying is implemented.

- GET `/api/browser/discovery` reports installed managed Chromium, detected browser sources and download state. POST `/api/browser/install {}` explicitly installs Playwright's pinned Chromium outside source.
- GET `/api/sessions/:id/browser` returns connection state and session-scoped tabs. POST `.../connect` accepts `BrowserConnectSchema`; POST `.../disconnect {}` tears down the connection. POST `.../tabs {url?}` opens a tab. Archived/unknown sessions reject.
- GET `.../tabs/:tabId/snapshot?image=true|false` returns bounded page text, accessibility targets and optional PNG. POST `.../action {action,clientId}` sends a human action only for its owning viewer. POST `.../control {owner,clientId}` performs an explicit handoff. Action schemas and navigation protocols are validated at the boundary.
- WS `/ws/browser?sessionId&tabId` uses the existing Host/Origin guard. A hello gives the ephemeral viewer ID. JPEG frames arrive as JSON metadata followed by binary data; the client acknowledges after decoding. Human input and explicit control requests are separate messages. Limits bound clients, payloads, queued input, frame pacing and slow viewers. A handoff drains current work and rejects queued writes from the old owner. Agent snapshots remain possible while a human controls a tab.
- POST `/api/browser/mcp` is an authenticated Streamable HTTP MCP endpoint. Every enabled provider run receives a random capability bound to its run/session, retained only as a hash on the server and revoked on completion/interruption. Provider events scrub its literal token before persistence. Codex uses per-thread MCP config with a bearer environment variable; Claude uses the SDK's HTTP MCP configuration. Neither edits global native provider configuration. Browser mutations require host approval once per Supervised/Auto-accept edits run; Auto/Full access use their selected policy. The gateway enforces human tab ownership regardless of provider policy. `browser.opened` opens the selected session's browser pane once per run.

`AppSettings.autoCompactPercent` accepts null (native defaults) or an integer 1–95. Subsequent runs map this to Claude's native percentage environment control or Codex's per-thread absolute token limit derived from provider capacity metadata. A missing Codex capacity produces a notice and preserves native compaction. Native reserves can cause earlier compaction. Progress is shown only when the provider reports a compaction event. See `provider-compaction-research.md` for the observed metadata limitations; triggering a paid compaction was not part of automatic checks.


## Repository operations and automatic context

`GET /api/projects/:id/repository?sessionId=optional` returns scoped local Git status, branches, eligible changed paths and an optimistic concurrency fingerprint. `GET .../github` separately reads cached GitHub PR/check/workflow status through the installed authenticated `gh` executable. Workflow status is read-only; no workflow mutation endpoints exist.

`POST .../repository/commit`, `/push`, `/branch` and `/pull-request` accept shared strict schemas and the displayed expected HEAD. Commit also requires selected paths and an expected status fingerprint. Mutations reject busy workspaces, unsafe paths and stale state; they never auto-push, reset, discard or merge. GitHub failures remain visible independently of local Git operations.

`GET /api/projects/:id/context` returns a durable bounded static project snapshot; `POST .../context/refresh {}` refreshes it. Project onboarding and ongoing file, repository and run observations refresh Tasks, Activity and Agent Map without paid background inference. SQLite migration 6 stores task sources and project context. Native provider plans report task steps; provider completion means Review. Actual manual field edits become per-field overrides. No dependency is inferred from plan ordering and no missing source is treated as completion. See repository-automation.md for data sources, behavior and limits.


## Group sessions

Cowork, Orchestrated and Current agent leads are implemented as a shared conversation and membership layer above the independent provider sessions. The detailed behavior is specified in phase-2-group-sessions.md; user controls are described in group-sessions.md. Migrations 7 and 8 add durable groups, members, messages, requests, deliveries, assignments, verified artifacts and explicit artifact prerequisites. Migration 8 also upgrades development databases that opened either earlier v7 shape, retaining artifact records and consumer links.

- `POST /api/groups CreateGroup` converts an idle session and adds an agent, with a separate coordinator only in Orchestrated mode. Existing history/native IDs stay with their sessions. New sessions use isolated worktrees by default. Creation starts no inference.
- `GET /api/groups/:id` returns `GroupSnapshot`; bootstrap includes group snapshots. `PATCH` changes mode/designated coordinator or limits with explicit idle/pending-work guards. Limit increases preserve recorded turn counts. `DELETE /api/groups/:id` pauses scheduling, cancels pending deliveries, stops all member runs/compactions and session terminals, then archives the group and member session metadata. Group/session conversation histories, recovery records, project files, worktrees and branches remain; browser connections are disconnected. Deleting a group is separate from removing an individual agent from its roster.
- `POST .../agents AddGroupAgent` adds an independent participant. `DELETE .../members/:memberId` removes an eligible idle member while retaining historical identity and workspace. Handles are unique, including retired handles; the anchor and designated coordinator cannot be removed directly. Active groups are not archived through the independent-session archive endpoint.
- `POST .../messages SendGroupMessage` saves one human message and queues intended deliveries. Explicit recipients are member IDs; the composer resolves mentions and shows the destination. Without explicit targets, Cowork runs one temporary planner before scoped peer assignments; coordinated modes dispatch the designated orchestrator. Native plan intent targets exactly one agent, persists with the request, and uses the same provider read-only mode as a session plan; browser/team side-effect tools are withheld and commands/skills are rejected. A user-approved plan is explicitly queued through the durable group delivery path, with its plan linked to the request and resulting run. The server also supports validated human-handle addressing for local API clients, ignoring code, quoted text and URLs. Model prose never dispatches work. Client message IDs deduplicate retries.
- `POST .../pause {}` holds scheduling. `POST .../stop {}` also interrupts every active member. `POST .../resume {}` explicitly clears holds/requeues eligible interrupted deliveries without resetting budgets. `POST .../members/:memberId/interrupt {}` stops that member and cancels its queued work; `.../resume {}` releases its hold and retries eligible interrupted work.
- Existing session send/interrupt endpoints respect group routing and stops. The original session is the group entry; its unaddressed sends use the group's routing. Provider identity changes are rejected for grouped members. Tasks Run dispatches through the group queue and retains the existing task ID.
- `PATCH /api/settings` stores `groupDefaults`: coordinator and worker configurations, maximum parallel runs, per-request turns and message hops. Existing members retain their effective configuration; provider capability validation remains enforced.
- `POST /api/team/mcp` exposes the six host-authenticated team tools to recorded group runs. Each random capability is bound to its invoking run, session, member, request and delivery. Sender identity is never supplied by the model. Authorization is rechecked before operations and after asynchronous artifact verification. Codex and Claude receive this MCP server independently of browser access, with literal tokens scrubbed from runtime events/errors.

The group scheduler claims a durable delivery and binds the native run before provider execution. Per-member serialization includes provider cleanup locks; completion, failure and interruption remain distinct. Only the orchestrator or Cowork request planner schedules assignments. Peers exchange compact targeted payloads and verified artifact references; informational updates do not start model turns. Questions can wake an eligible member within the recorded budget. Same-workspace edit scopes and task ownership are checked. Explicit artifact dependencies can unblock a consumer while a producer remains in Review; legacy prerequisites require Done. Referencing an artifact does not merge it.

Live text remains session/message-scoped, preserving concurrent streams. Group mutations emit existing state notifications; shared timelines merge durable group entries and original native messages, suppressing duplicated delivery prompts. Recovery marks active deliveries interrupted and pauses unfinished scheduling. No paid work resumes merely because Mingle restarted. Human native commands and supported skills target one member through the invocation contract above; ordinary messages preserve the group's existing routing. A paid provider-backed integrated demonstration remains separate from source implementation and local checks.

Group delivery snapshots also expose their durable dispatch `kind` (`request`, `assignment`, `message`, `result`), optional for older snapshots. The conversation ends with a compact latest-request result summary derived from recorded deliveries, task states, native final responses and run change snapshots. Worker summaries prefer their assignment runs; the planner report prefers its result follow-up, so late completion acknowledgments cannot replace the work report. Source labels distinguish agent reports from host records; finished turns do not certify integration, checks or task acceptance. Pending work, interruption, failure, missing history and Review remain explicit. No extra inference or task-state mutation is needed to display the summary. Native guidance asks the coordinator for one human-facing outcome, named contributions, integration location, actual versus reported checks and remaining work; workers avoid repetitive completion messages.

## Google accounts and portable preferences

Mingle accounts are separate from provider authentication and local workspace access. Google sign-in uses Supabase PKCE through an ephemeral loopback callback with one-time state; `getUser()` verifies the account before exposing public identity. The renderer receives no Supabase session tokens. Electron wraps a random encryption key with OS safeStorage and passes it over a private, request-correlated child IPC channel that remains available for explicit storage retries. Node persists only authenticated AES-GCM ciphertext outside source. Unavailable keyrings and Node-only runtimes use explicitly labelled memory-only sessions. No keyring plaintext fallback is accepted.

`GET /api/account` returns `AccountState`; `PUT /api/account/connection` stores public custom deployment configuration; `POST /api/account/sign-in`, `DELETE /api/account/sign-in` and `POST /api/account/sign-out` start/cancel/end this device's account session. All mutations use the local runtime's existing Host/Origin checks. Login URLs are ephemeral and errors never include codes/tokens. `GET /api/account/preferences` requires a verified Google account and returns a nullable saved version; `PUT` validates an explicit portable preference allowlist and expected revision. Stale saves return 409. The shared account contracts are in `packages/contracts/src/account.ts`.

Supabase `account_preferences.user_id` references `auth.users.id`; owner-only RLS covers all CRUD operations. No anonymous grants or service-role clients are used. Settings → Account explicitly saves/restores theme, provider/model/effort defaults and compaction threshold. Restores use the normal settings validation path, retain existing sessions, and never sync permissions or machine data. Account login does not partition the OS user's local SQLite data. Team membership references the stable verified account UUID and has separate authorization in the distributed layer below. See [accounts](accounts.md) for deployment, Google testing-mode limits and verification evidence.

## Resilience, checkpoints and manual compaction

Migration 11 adds optional group autonomy/recovery policy/state, coordinator epochs, durable session checkpoints and per-run provider failures, idempotent group recovery actions, supervised batch checkpoints, assignment milestones and bounded stall evidence. All records are local SQLite runtime data. The exact TypeScript contracts and HTTP payloads are documented in [resilience.md](resilience.md); public snapshot extensions remain optional so older saved settings and snapshots continue to load.

Group autonomy is `supervised`, `balanced` or `extended` (new defaults use `balanced`). New group turn defaults are 80 with a schema ceiling of 10,000; existing explicit limits, including saved 16-turn limits, are not migrated or silently rewritten. `autonomy.emergencyTurnLimit` omitted inherits the legacy group ceiling, `null` disables the turn ceiling, and a number explicitly replaces it. Automatic fallback is off unless `recoveryPolicy.automaticFallback` and a specific existing eligible member are configured. An unknown quota pool remains paused unless the group's advanced `recoveryPolicy.allowUnverifiedQuotaFallback` opt-in is enabled; that permits one bounded attempt and does not claim independent or available quota. Fallback preserves that member's native provider conversation, model, effort, permissions and policy; Mingle never substitutes a provider in-place.

Session checkpoints retain bounded task criteria, Git HEAD/branch/dirty-path metadata, artifact references, pending approval summaries, redacted errors and uncertain tool summaries. They do not contain source files, approval inputs, tool input/output, provider credentials or fabricated completion evidence. Failed Git inspection is explicit (`statusKnown: false`) rather than represented as a clean worktree. Provider failure records are run-addressable; `retryable` is informational and does not authorize replay. Only positive `safeToRetry` evidence can permit safe automatic retry. Unknown host-side mutation outcomes stay paused for explicit human recovery; restart never automatically resumes paid work. Lead replacement increments an authority epoch and atomically updates actionable request planner ownership; stale lead tools are fenced while independent in-flight workers can finish.

Unclean-start recovery also captures the interrupted session state after pending approvals and tools are marked interrupted; outstanding checkpoint captures are drained before the SQLite connection closes.

`GET /api/sessions/:id/recovery` returns `{checkpoint,failure}`. `POST /api/sessions/:id/checkpoints` accepts `{reason,runId?}` and captures a durable metadata snapshot. `POST /api/groups/:id/recovery` accepts the shared idempotent recovery-action union for retry-with-approach, reassign/fallback to a chosen existing member, coordinator replacement, Ask me/pause, checkpoint acknowledgement, or explicit resume. Recovery actions are not accepted based on stale coordinator authority or duplicated idempotency keys.

`POST /api/sessions/:id/compact {operationId?}` targets exactly one native conversation and returns `ContextCompactionResult` with status, timestamps, checkpoint reference, visible message and error. An optional operation ID identifies the request; `POST /api/sessions/:id/compact/interrupt {operationId}` interrupts only that matching operation, so a stale Stop cannot cancel a later compaction or run. Compaction reserves the same per-session active/cleanup lock as a run before its first asynchronous step, exposes busy state, and releases only after provider cleanup; interruption and shutdown signal the native operation. Native compaction never becomes a regular model prompt or grants tool/permission authority. Codex app-server supports `thread/compact/start`; Claude uses the native `/compact` command only when the resumed SDK advertises it; OpenCode uses its native local-session summarize endpoint when the active native session can be bound. Antigravity manual compaction is unsupported. Other cases return `unsupported` rather than simulate a summary. See `provider-design.md` in the resilience coordination directory for dated source references and validation limits.


## Distributed team workspaces

`DistributedWorkspaceService` composes verified account/team authority, per-team registered devices, encrypted outbound mailbox transport, exceptional remote execution, controlled Git bundles and restricted remote commands. All `/api/distributed/*` routes retain the local Host/Origin checks. Teams, invitations, projects, device keys/links and ciphertext mailboxes use the reviewed additive Supabase migration; local service tables are added idempotently to the existing SQLite store. Applying cloud SQL is a separate deployment action.

Settings → Team workspace exposes People, Projects, Devices, Agents/map, Conversation, Recovery, and Transfers using actual snapshots. Account or schema failures are visible. Selected Claude, Codex and OpenCode sessions can be explicitly published regardless of their saved policy; linking/publishing never invokes inference. Explicit team-owner consent and the most restrictive session/team/consent policy bound team deliveries. Provider credentials remain local. Membership, device ownership, mutual fingerprint pins and request digests are checked before authority is consumed. Native tool approvals during a remote run also require the destination owner. All Git mutations share the existing local repository/runtime lease.

Automatic remote fallback requires durable quota/provider failure evidence, safe continuation, a committed clean checkpoint, and exhausted eligible local alternatives. Unknown, busy, or available local alternatives block it. Explicit unpublished-work recovery is human-only. Destination execution checks that source commits and committed artifact references exist locally, the destination is clean, and the exact owner consents to one provider run. Quota stays unknown when unreported; progress sharing defaults off. No restart automatically replays uncertain provider or command dispatches.

Git transfer requires source approval before sending bundle bytes and receiving-owner approval before import into isolated refs. Merge and push are separate exact local approvals. Remote commands are a fixed typed read-only Git operation union with local project binding, path/symlink checks and audit records; this is not an OS sandbox. Shared tasks/messages and consented progress retain authenticated account/device identity and source group IDs. See [runbook](distributed-workspaces.md), [transport API](distributed-transport-api.md), [execution API](distributed-execution-api.md), [Git API](distributed-git-api.md), and [UI API](distributed-ui-api.md) for interfaces and validation limits.
