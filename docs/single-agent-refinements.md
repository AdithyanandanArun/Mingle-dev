### 3 — Long conversations

- Standalone sessions open on the bootstrap's newest 300 messages. A "Load older messages" control at the top pages `GET /api/sessions/:id/messages?before=<oldest displayed id>&limit=101` on demand only (one extra row answers "is there more" without another request; no idle polling). Loading, failure (with the server's message and Retry) and "Start of conversation" are shown from real state. A session whose bootstrap holds fewer than 300 messages is complete, so it shows no control.
- Older history lives in `apps/web/src/lib/sessionHistory.ts`, outside the refresh store. It is held contiguously (`older ++ bootstrap window`), the bootstrap's copy always wins, messages that slide out of the bootstrap window while a session is open are kept in place, and a window that cannot be proven contiguous (300+ new messages unseen) discards the held history with a visible notice instead of showing a hole. Requests are fenced by an abort signal, an epoch and the cursor they were issued for, so session switches, unmounts, late responses, overlapping clicks and duplicate pages cannot reorder, duplicate or resurrect history.
- Memory: at most 6 sessions are remembered; a session that is left keeps its 400 nearest older messages (the rest reload on demand). An open session retains at most 5,000 older messages, including messages that leave the live window. Overflow evicts the farthest older rows with a visible notice, retains a contiguous recent window, and fences requests tied to the evicted history. Paging also respects this cap, including a final page that would cross it.
- The server now answers an unknown or other-session `before` cursor with the same 404 message, without leaking identity or silently returning the newest page. An empty cursor is invalid input (400); the store returns nothing for a foreign cursor.
- Prepending keeps the reader on the same row (anchor restored after the insert and while deferred rows settle), does not pin to the bottom or count as new output, adds no arrival animation, and silences the conversation live region briefly so assistive technology is not asked to read out the prepended rows. Run activity, tool and change cards are placed by the existing layout, so runs whose messages were older than the window (previously listed after the latest message) move under their own user messages as their history loads.
- Rendering: rows use `content-visibility: auto` with remembered intrinsic heights. This is deferred layout/paint, **not virtualization**: React and Markdown still mount every loaded row and all text stays in the DOM, so selection, copy, native find (which reveals skipped rows), focus and screen readers keep working. A column observer keeps the view pinned while rows take their real height, and "Latest" now jumps instantly for that reason (a smooth scroll targeted a height that changed underneath it).
- Checks: web TypeScript and 116 unit tests (20 new history tests); server TypeScript and 6 new cursor tests; browser acceptance `node scripts/session-history-browser-acceptance.mjs` (real SessionPane over an Example 600-turn transcript, three consecutive passes) plus the existing render-count, 30 workflow/composer, 7 status-bar and 8 automatic-subagent browser checks. Fixture evidence on Chromium: 300 mounted rows, 300 skipped initially; with all 1,210 messages loaded 1,205 rows skip layout (36.5k DOM nodes remain mounted); eight forced full-column relayouts cost ~130–165 ms with deferral vs ~375–435 ms with everything rendered; anchor shift after prepending 0.2 px; 11 requests to load the whole history with 100 messages each. The full parallel server suite shows load-related timeouts in unrelated distributed/team tests that all pass when run alone.
- Limitations: pages carry messages only, so run/tool/change cards exist only for the runs the bootstrap already holds (newest 200); older user messages load without run cards. The 300-message window is duplicated in the web client (a server test fails if it changes). Browsers without `content-visibility` render every row (correct, no saving). `innerText` of a skipped row is empty (selection, `textContent` and find still see it). Measurements are fixture evidence on one machine, not a latency guarantee.

### 4 — Reduce refresh traffic

- Contract: `GET /api/sessions/:id/snapshot` returns a read-only `SessionSnapshot`, defined as exactly the rows `/api/bootstrap` carries for that session (row, newest 300 messages, runs, tool calls, queue, approvals, plans, questions, goal, helper records). The bootstrap's *global* limits (200 runs, 1,000 tool calls, 50 resolved approvals, 300 plans/questions) are ranked on row ids only and then filtered to the session, so a slice equals the bootstrap's rows at every cap while pending approvals stay uncapped; nothing else is materialized, and there is no provider discovery, cloud or inference call. It is one synchronous read. Group members, shared-team proxies and helper sessions answer 409 (their state spans shared rows); unknown or archived sessions 404. `eventCursor` is diagnostic only: unrecorded changes do not move it, so no client treats it as a freshness fence.
- Notifications: `Store.touch(sessionId?)` and an optional `state.changed.scope` (`sessionIds`, at most 8). The runtime passes the exact session for tool activity/output, subagent text, tool and info messages, usage and the first streamed message; plan, question and queue rows scope their own session. The server also scopes a narrow event allowlist (approval requested/resolved/denied/expired, question asked/answered/cancelled, plan updated/approved/edited, queue start-failed, progress status). Any unscoped touch in the 60 ms window, or more than 8 sessions, widens the notification to a full change. Run started/finished and every task, group, project, team, workflow or unknown event stay unscoped: they also change tasks, goals or project context.
- Client: `refreshCoordinator.ts` serializes refreshes. Notifications only mark what is stale; the existing debounced scheduler (160 ms debounce, 1 s floor, 2 s ceiling) decides when to `flush`, so scoped refreshes keep the same pacing and nothing polls. Marks made while a request is in flight are not covered by it and get a trailing request when the next flush is demanded; a full refresh supersedes queued scoped marks; an explicit `refreshNow()` still resolves only after a full request that started after the call. Scoped refresh is used only for a known standalone session (not a group member, helper or selected team session), at most four per cycle. A failed, 404/409, malformed or wrong-session answer is never merged: it falls back to a full refresh, puts that session on full refreshes for 30 s and, after three consecutive failures, disables scoped refresh until the next connection (older servers without the endpoint). Reconnect, stream gaps, unknown/global events and explicit refresh use the full bootstrap. A session archived or converted to a group while its answer was in flight is discarded or escalated, and sessions archived in this window are filtered from a full snapshot issued before the archive.
- Preserved: optimistic messages (kept until a saved copy arrives), live stream text (never pruned past the snapshot), the 32 ms stream publish batching, state identity reuse (only the session's rows are replaced, every other reference stays; an unchanged snapshot changes nothing), and the 300-message window item 3's history cursor assumes. Live-appended events are now trimmed to the bootstrap's 500-event window.
- Checks: server TypeScript, contracts TypeScript, web TypeScript; full server suite run serially (102 files, 754 tests, 7 new covering slice equality at every cap, eligibility, no provider discovery, read-only behaviour, scope coalescing/widening, the event allowlist and live run scoping); all 166 web tests (50 new: coordinator barriers, store-level full-vs-scoped, mid-flight, reconnect, archive/group conversion, 404/failed/malformed fallback, optimistic and stream preservation, event window, merge/validation); browser acceptance `node scripts/scoped-refresh-browser-acceptance.mjs` (real server with a scripted fake provider, real web app in Chromium, Example workspace, two consecutive passes) plus the existing history, automatic-subagent (8), workflow/composer (30), chat render-performance and status-bar (7) browser checks.
- Fixture evidence (loopback, one machine; not Internet latency, CPU or memory): 30 Example sessions x 150 messages, a full bootstrap is 2,379,846 B and a session snapshot ~82,900 B (28.7x smaller; the server-side fixture measured 2,285,569 B vs 76,058 B). One scripted run with 12 tool calls (5.5 s) on the base commit made 6 whole-bootstrap requests (14,261,004 B); now it makes 2 whole-bootstrap requests (run start and finish, 4,753,721 B) plus 4 snapshots of the active session only (331,755 B): the same 6 requests but 5,085,476 B in total (2.8x less) and 3x fewer whole-workspace reloads. The store test over 41 sessions / 10,817 messages shows 20 activity cycles costing 20 snapshots (1,911,680 B) instead of 20 bootstraps (69,322,920 B). Idle pages made 0 refresh requests over 4 s, and a dropped socket produced a full bootstrap and no snapshot.
- Limitations: request counts do not fall for short runs (the 1 s floor already bounded them); the saving is payload, and the run start/finish bootstraps dominate what is left. Concurrently active sessions beyond four per cycle, helpers, group and team sessions still reload everything. Each snapshot ranks run/tool ids across the whole workspace, which is cheap on the fixture but its CPU cost was not measured. The unchanged `mingle:state-changed` window event still makes the file tree and repository panels fetch their own data on every notification, scoped or not. A session archived locally keeps orphan message rows until the next full refresh (the archive route's event triggers one). Measurements are fixture evidence, not a latency guarantee.

### 5 — Tool output

- Before: a snapshot's tool copy is a 4,000-character input head and 2,000-character output tail, and its `outputTruncated` flag meant either "capture clipped at 20,000 characters" or "this copy was shortened". Every change to an expanded tool's own record re-ran its detail fetch (three lifecycle updates made three extra requests on the fixture) and the UI could not tell an unchanged tail from changed output, so a held full copy was either refetched or kept past its content. Labels said "Captured output" for text that was only a tail.
- Contract (additive, optional): `ToolCall.revision` rises with every stored change; `contentRevision` is the revision at which input/output last changed; `preview` appears only on a shortened copy and gives the stored `inputChars`/`outputChars`. `outputTruncated` now means only that capture clipped the output. Records stored before this change report revision 0; the runtime no longer rewrites (or re-versions) a record whose stored fields did not change, so a run ending does not invalidate completed tools. Recovery marking a running tool interrupted bumps `revision`. No overlapping text is ever joined or guessed.
- Client: `apps/web/src/lib/toolRecords.ts` reconciles versions by number. Lifecycle facts come from the higher `revision`; input/output from the higher `contentRevision` (a complete copy beats a preview of the same content); an older response never replaces a newer record; an unversioned fixture copy simply wins. A completed row asks for the complete record only when it is open and the held copy is a preview, once per content version; running tools are never fetched. Closing, a newer content revision, unmounting or an error ends the request's effect; reopening retries. Opening a run's list now also seeds each row's complete copy, so rows it covers need no per-tool request.
- Summaries: the run line is built from the run's category counts (`Ran 3 commands · 1 search · 1 file action`) plus outcome counts from loaded calls only when all reported calls are loaded (`1 failed · 1 call exited non-zero`). Rows show recorded exit code, duration and child-call count. Nothing is derived from a tool's name or text; a command called "test" that exited 0 is never summarised as passing. At widths below 600px the summary wraps under the status instead of being hidden, and a row's command wraps under its title. Labels state what is shown: `Output tail · last 2,000 of 11,234 characters`, `Output · last 20,000 characters captured (earlier output was not kept)`, `Input · first 4,000 of 13,401 characters`. The standalone subagent drill-down uses the same reconciler and labels.
- Checks: contracts/web/server TypeScript (worktree contracts via a temporary tsconfig); 17 new web unit tests (reconcile ordering, stale rollback, lifecycle-only updates, labels, summaries) in 183 total; 4 new server tests (revision ordering, no rewrite at run end, preview metadata at bootstrap/snapshot/detail/list, legacy rows and recovery); browser acceptance `node scripts/tool-output-browser-acceptance.mjs` (real SessionPane over an Example run, 14 checks, three consecutive passes, screenshots at 390px and 1,100px inspected) plus the existing automatic-subagent (8), session-history, chat render-performance, scoped-refresh, workflow/composer (30) and status-bar browser runs; the full server suite ran serially (103 files, 758 passed, 1 skipped). Browser runs used a disposable /tmp copy whose `@mingle/contracts` resolves to this worktree.
- Fixture evidence: three lifecycle-only updates to an expanded completed tool: 3 extra detail requests before, 0 after; three unrelated snapshots: 0 requests; one genuinely changed output: exactly 1 refetch, with the bounded tail shown (and labelled) while it loads; opening a run with a working list: 1 list request and 0 tool requests before any row is expanded.
- Limitations: opening a run still downloads the run list of complete records (up to 1,000 x 20,000 characters), as before; a complete copy lives only while its run activity is mounted. A record whose capture clipped output cannot show what was not stored. The acceptance's tool endpoints are in-page stand-ins that follow the server's rules (the real rules are covered by the server tests); fixture timings and counts are not live-provider guarantees. The completion-review card remains item 6.

### 6 — Completion review

- Finished turns with saved changes, recorded tool activity, a failure/interruption, an autonomous-goal turn or a reported checklist get one review card at the existing transcript placement. Turns with only non-command failures still get a card. It embeds the existing saved change list and diff dialog, with no duplicate Changes card. Tasks and checklist state remain in Review for the person to accept.
- The card separates Mingle-recorded changes, command/tool outcomes and classified provider failures from the agent's exact-run goal report and per-run checklist. Exit 0 is reported as `exit 0`; it is never called a passing test. No test counts/results are inferred from command names or prose. A completed provider turn does not verify the goal, and absent change capture, commands, reports or checklist evidence are labelled as absent/unknown.
- `GET /api/runs/:id/review` is a read-only, bounded metadata seam. SQL counts every stored tool call while returning at most 50 commands and 20 problems, without tool input/output; clipped command text and provider failure messages are redacted. Goal reports come from that exact durable run row. The client uses exact per-run task sources, not the workflow's latest summary. It fetches evidence only for the newest/goal-latest review or when older details are opened; errors can be retried, and abort/key fences discard stale, closed and unmounted answers. Tool lifecycle revisions invalidate evidence even when the run's total call count is unchanged.

### 7 — Actionable recovery

- The existing Composer failure area now uses only the server's classified failure kind/code for recovery guidance. It is shown only when the stored `runId` still identifies a failed run for the session's current provider/model; stale or unclassified session errors get a generic review action and never a guessed cause. Auth points to local Providers settings (which documents provider CLI sign-in separately from Mingle account sign-in), quota opens provider usage, context exhaustion prepares `/compact` in the draft without sending it, and failures link to the matching run review. Pending question/approval links scroll to and focus the actual existing cards. Paused autonomous goals continue to use their single SessionWorkflowPanel for versioned Resume and displayed turn/deadline limits.
- Durable replay is deliberately limited to generated workflow `continue` and `verify` turns. Before provider dispatch, the run row saves the exact provider prompt and injected context. If the strict evidence gate passes, an additive SQLite retry ledger binds that saved prompt/context to the workflow, task, native provider conversation and pinned provider/model/effort/policy/worktree configuration. One atomic claim links the failed original attempt to one consumed retry before provider start; a retry attempt cannot schedule another retry. The retry spends one normal turn from the same budget and deadline.
- Eligibility comes from `RecoveryService.failureForRun` and requires a retryable `temporary_rate_limit` or `provider_unavailable`, `safeToRetry === true`, `dispatchState === 'not-dispatched'`, `outcomeUnknown === false`, and `continuationSafety === 'safe'`. Missing evidence, refusal codes, shutdown/interruption, denied/expired/cancelled approvals or questions, recorded tools, known workspace changes, unknown changes, unavailable exact prompt/context, missing native conversation IDs, and exhausted turn/deadline budgets fail closed. The scheduler waits for a bounded `retryAt`; it reuses the workflow's single cancellable timer with the deadline. Queue work keeps priority. Pause, Stop, configuration changes, archive/group conversion, cleanup, queued input and new human work fence or cancel the pending claim. A restart cancels pending claims and pauses the workflow as app-closed for manual review. No generic retry endpoint, arbitrary user prompt replay, provider switch, or permission/settings escalation is used.
- The Composer distinguishes a pending generated-workflow retry from a paused/manual failure and keeps cause actions tied to the failed run's current provider/model. A new focused browser section exercises authentication setup versus Mingle account guidance, usage, the run-review link, pending retry copy, mismatched-model fencing, keyboard activation, and question/approval-card focus. Recovery action links have spacing at narrow widths.
- Checks: contracts, web and server TypeScript using the disposable `/tmp/item7-r2` copy with this worktree's contracts aliases; 26 workflow service tests, including eligible one-shot retry, no third attempt after retry failure, strict missing/unsafe/refusal rejection, pause, restart and configuration-change fences; 65 workflow/runtime/recovery regression tests; 3 `providerFailureUi` tests; browser acceptance `session-workflow-browser-acceptance.mjs` (31 checks, including the real Composer/store recovery actions, keyboard and 390px/900px layouts); and `run-review-browser-acceptance.mjs` (17 checks). Browser fixtures used only explicitly labelled Example data and local mocked endpoints; no provider or cloud calls. Parent rechecked item 6's five previously failing files separately: all 30 tests passed (`/tmp/mingle-item6-focused-recheck.log`). These are focused checks, not a full server-suite result.
- Limits: automatic retry requires a persisted native provider conversation ID and exact prompt/context captured before dispatch. Providers that do not report those IDs, failures without complete safe evidence, and user/start/resume/queue/native/plan/attachment turns remain manual. The bounded retry ledger is local SQLite runtime state. The run-review route suite passed separately in the direct worktree recheck (7 tests); the prior disposable-harness error was a harness-only resolution issue and is not a product failure.

### 8 — Understandable context inspector

- The advanced conversation popover now includes a compact context inspector for selected attachments, file and quote references, a fresh project-memory recall preview, and saved memory injection/exclusion metadata from recent runs. It labels previews as previews and historical entries by their saved title/revision; it explains that bodies may have changed. File contents stay server-resolved when a run starts. Provider context limits and current context occupancy are explicitly unreported; Usage describes cumulative session totals and does not present them as occupancy. Compaction copy describes provider-controlled summarization without claiming exact retained content.
- A strict `memory: "exclude"` run option skips both automatic recall and all run-scoped project-memory tools. It is standalone-session scoped; groups reject it. The checkbox remains selected after failed requests and clears after successful send. Steering requests carrying exclusion queue for the next turn instead of implying an already-running provider context changed. Queued records persist the choice in SQLite; normal queue delivery applies it to that item. Workflow start can exclude its first run only; autonomous continuations return to default memory. The run exclusion is saved separately from memory injection logs so a skipped recall is not recorded as an injection. Exact-context workflow retries skip new recall and inherit an excluded source run’s memory-tool boundary. The UI says exclusion cannot erase material already present in native provider history.
- Checks: contracts, server and web TypeScript; 50 focused project-memory, queue/session and workflow tests; the context inspector browser acceptance (1 focused scenario at 390px); full session-workflow Composer browser acceptance (32 scenarios after adding the inspector case). The server tests assert inclusion and memory tools by default, both absent under exclusion, next-request reset, session isolation, invalid values, queue persistence/delivery, and first-workflow-run exclusion followed by a memory-enabled continuation. Browser routes are local Example stand-ins only; no provider inference or cloud request is made.
- Limits: the inspector is a bounded recent-injection record list and preview, not a reconstruction of arbitrary native provider history. A preview query can differ from the eventual run query after prompt or project state changes. Token counts are session cumulative totals only; provider context limits/current occupancy are unreported by this feature. Workflow exclusion is only configurable at goal start; subsequent autonomous turns use memory normally.

### 10 — Draft and reader continuity

- Standalone session draft text and reader position use one bounded, validated browser-local cache per origin. It retains at most 32 sessions, 20,000 characters per draft, 120,000 draft characters total and 480,000 UTF-8 draft bytes total. Draft text saves after edits with a short debounce and on page lifecycle; attachment bytes, transcripts, tool output and context references are not serialized, and provider/account credential stores are not read or copied. Draft text itself is stored locally as entered. Existing server-owned attachment drafts still load through their session API. A successful send consumes the saved text only if it still matches the text that was submitted; failures and newer edits remain in the Composer. Context references continue through the existing server validation when a message is sent.
