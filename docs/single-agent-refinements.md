# Single-agent refinements

Approved 4 November 2026. Base: Mingle 0.1.0 (`f27ea09`). Implement in the order below, with a focused local commit and relevant checks for each item. Publication is separate.

Keep native conversations, provider availability and permissions truthful. Preserve autonomous budgets, user stops, approval boundaries and uncertainty about side effects. Use flat neutral surfaces, restrained motion and reduced-motion support. Tests use disposable examples and fake providers; no paid inference or cloud writes.

| 1 | Simplify composer | Complete | One Chat / Plan / Autonomous selector; model and permissions stay visible; advanced effort, tier and goal budgets move into a keyboard-accessible popover. Existing commands, attachments, context, paused-goal chat and configuration locks still work. |
| 2 | Unify progress | Complete | One expandable progress surface combines current task, goal, helpers and run state. Pause/Stop/Resume, checklist and helper navigation remain accessible without stacked status panels. |

## Validation approach

- Run direct TypeScript and focused Vitest/Node checks for substantive changes.
- Exercise real UI components with the repository's documented local browser acceptance harnesses. Label all fixture data as examples.
- Add regression coverage for concurrency, lifecycle, pagination and permission boundaries; avoid tests that simply repeat implementation details.
- Record measurements as fixture evidence, never Internet latency or live-provider guarantees.
- Run integrated web/server checks after the ordered changes and record remaining limitations.

### 3 — Long conversations

- Standalone sessions open on the bootstrap's newest 300 messages. A "Load older messages" control at the top pages `GET /api/sessions/:id/messages?before=<oldest displayed id>&limit=101` on demand only (one extra row answers "is there more" without another request; no idle polling). Loading, failure (with the server's message and Retry) and "Start of conversation" are shown from real state. A session whose bootstrap holds fewer than 300 messages is complete, so it shows no control.
- Older history lives in `apps/web/src/lib/sessionHistory.ts`, outside the refresh store. It is held contiguously (`older ++ bootstrap window`), the bootstrap's copy always wins, messages that slide out of the bootstrap window while a session is open are kept in place, and a window that cannot be proven contiguous (300+ new messages unseen) discards the held history with a visible notice instead of showing a hole. Requests are fenced by an abort signal, an epoch and the cursor they were issued for, so session switches, unmounts, late responses, overlapping clicks and duplicate pages cannot reorder, duplicate or resurrect history.
- Memory: at most 6 sessions are remembered; a session that is left keeps its 400 nearest older messages (the rest reload on demand); an open session stops offering more at 5,000 older messages and says so.
- The server now answers an unknown, empty or other-session `before` cursor with 404 (same message for both, no identity leak) rather than silently returning the newest page; the store returns nothing for a foreign cursor.
- Prepending keeps the reader on the same row (anchor restored after the insert and while deferred rows settle), does not pin to the bottom or count as new output, adds no arrival animation, and silences the conversation live region briefly so assistive technology is not asked to read out the prepended rows. Run activity, tool and change cards are placed by the existing layout, so runs whose messages were older than the window (previously listed after the latest message) move under their own user messages as their history loads.
- Rendering: rows use `content-visibility: auto` with remembered intrinsic heights. This is deferred layout/paint, **not virtualization**: React and Markdown still mount every loaded row and all text stays in the DOM, so selection, copy, native find (which reveals skipped rows), focus and screen readers keep working. A column observer keeps the view pinned while rows take their real height, and "Latest" now jumps instantly for that reason (a smooth scroll targeted a height that changed underneath it).
- Checks: web TypeScript and 116 unit tests (20 new history tests); server TypeScript and 6 new cursor tests; browser acceptance `node scripts/session-history-browser-acceptance.mjs` (real SessionPane over an Example 600-turn transcript, three consecutive passes) plus the existing render-count, 30 workflow/composer, 7 status-bar and 8 automatic-subagent browser checks. Fixture evidence on Chromium: 300 mounted rows, 300 skipped initially; with all 1,210 messages loaded 1,205 rows skip layout (36.5k DOM nodes remain mounted); eight forced full-column relayouts cost ~130–165 ms with deferral vs ~375–435 ms with everything rendered; anchor shift after prepending 0.2 px; 11 requests to load the whole history with 100 messages each. The full parallel server suite shows load-related timeouts in unrelated distributed/team tests that all pass when run alone.
- Limitations: pages carry messages only, so run/tool/change cards exist only for the runs the bootstrap already holds (newest 200); older user messages load without run cards. The 300-message window is duplicated in the web client (a server test fails if it changes). Browsers without `content-visibility` render every row (correct, no saving). `innerText` of a skipped row is empty (selection, `textContent` and find still see it). Measurements are fixture evidence on one machine, not a latency guarantee.

### 4 — Reduce refresh traffic

- Contract: `GET /api/sessions/:id/snapshot` returns a read-only `SessionSnapshot`, defined as exactly the rows `/api/bootstrap` carries for that session (row, newest 300 messages, runs, tool calls, queue, approvals, plans, questions, goal, helper records). The bootstrap's *global* limits (200 runs, 1,000 tool calls, 50 resolved approvals, 300 plans/questions) are ranked on row ids only and then filtered to the session, so a slice equals the bootstrap's rows at every cap while pending approvals stay uncapped; nothing else is materialized, and there is no provider discovery, cloud or inference call. It is one synchronous read. Group members, shared-team proxies and helper sessions answer 409 (their state spans shared rows); unknown or archived sessions 404. `eventCursor` is diagnostic only: unrecorded changes do not move it, so no client treats it as a freshness fence.
- Notifications: `Store.touch(sessionId?)` and an optional `state.changed.scope` (`sessionIds`, at most 8). The runtime passes the exact session for tool activity/output, subagent text, tool and info messages, usage and the first streamed message; plan, question and queue rows scope their own session. The server also scopes a narrow event allowlist (approval requested/resolved/denied/expired, question asked/answered/cancelled, plan updated/approved/edited, queue start-failed, progress status). Any unscoped touch in the 60 ms window, or more than 8 sessions, widens the notification to a full change. Run started/finished and every task, group, project, team, workflow or unknown event stay unscoped: they also change tasks, goals or project context.
- Client: `refreshCoordinator.ts` serializes refreshes. Notifications only mark what is stale; the existing debounced scheduler (160 ms debounce, 1 s floor, 2 s ceiling) decides when to `flush`, so scoped refreshes keep the same pacing and nothing polls. Marks made while a request is in flight are not covered by it and get a trailing request when the next flush is demanded; a full refresh supersedes queued scoped marks; an explicit `refreshNow()` still resolves only after a full request that started after the call. Scoped refresh is used only for a known standalone session (not a group member, helper or selected team session), at most four per cycle. A failed, 404/409, malformed or wrong-session answer is never merged: it falls back to a full refresh, puts that session on full refreshes for 30 s and, after three consecutive failures, disables scoped refresh until the next connection (older servers without the endpoint). Reconnect, stream gaps, unknown/global events and explicit refresh use the full bootstrap. A session archived or converted to a group while its answer was in flight is discarded or escalated, and sessions archived in this window are filtered from a full snapshot issued before the archive.
- Preserved: optimistic messages (kept until a saved copy arrives), live stream text (never pruned past the snapshot), the 32 ms stream publish batching, state identity reuse (only the session's rows are replaced, every other reference stays; an unchanged snapshot changes nothing), and the 300-message window item 3's history cursor assumes. Live-appended events are now trimmed to the bootstrap's 500-event window.
- Checks: server TypeScript, contracts TypeScript, web TypeScript; full server suite run serially (102 files, 754 tests, 7 new covering slice equality at every cap, eligibility, no provider discovery, read-only behaviour, scope coalescing/widening, the event allowlist and live run scoping); all 166 web tests (50 new: coordinator barriers, store-level full-vs-scoped, mid-flight, reconnect, archive/group conversion, 404/failed/malformed fallback, optimistic and stream preservation, event window, merge/validation); browser acceptance `node scripts/scoped-refresh-browser-acceptance.mjs` (real server with a scripted fake provider, real web app in Chromium, Example workspace, two consecutive passes) plus the existing history, automatic-subagent (8), workflow/composer (30), chat render-performance and status-bar (7) browser checks.
- Fixture evidence (loopback, one machine; not Internet latency, CPU or memory): 30 Example sessions x 150 messages, a full bootstrap is 2,379,846 B and a session snapshot ~82,900 B (28.7x smaller; the server-side fixture measured 2,285,569 B vs 76,058 B). One scripted run with 12 tool calls (5.5 s) on the base commit made 6 whole-bootstrap requests (14,261,004 B); now it makes 2 whole-bootstrap requests (run start and finish, 4,753,721 B) plus 4 snapshots of the active session only (331,755 B): the same 6 requests but 5,085,476 B in total (2.8x less) and 3x fewer whole-workspace reloads. The store test over 41 sessions / 10,817 messages shows 20 activity cycles costing 20 snapshots (1,911,680 B) instead of 20 bootstraps (69,322,920 B). Idle pages made 0 refresh requests over 4 s, and a dropped socket produced a full bootstrap and no snapshot.
- Limitations: request counts do not fall for short runs (the 1 s floor already bounded them); the saving is payload, and the run start/finish bootstraps dominate what is left. Concurrently active sessions beyond four per cycle, helpers, group and team sessions still reload everything. Each snapshot ranks run/tool ids across the whole workspace, which is cheap on the fixture but its CPU cost was not measured. The unchanged `mingle:state-changed` window event still makes the file tree and repository panels fetch their own data on every notification, scoped or not. A session archived locally keeps orphan message rows until the next full refresh (the archive route's event triggers one). Measurements are fixture evidence, not a latency guarantee.
