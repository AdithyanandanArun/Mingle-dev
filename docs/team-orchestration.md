# Cross-device team orchestration

Goal: agents on different teammates' devices work together exactly like a local multi-agent group — one orchestrator, workers, handoffs, a result card — with the team lead able to restructure the team interactively. Shared types live in `packages/contracts/src/team-orchestration.ts`.

## Product rules

1. **Current session by default.** Teammates setup shares the current conversation through `POST /api/projects/:projectId/team-orchestration/share-session`, using its agent as orchestrator. The setup panel asks only for the group-wide `permissionLevel` (`supervised` or `full-access`), which is the policy of the canonical team-session anchor; changes to that session policy update the team permission and proxy policies. Existing shared sessions stay authoritative. Advanced routing and fallback management remain in Team structure, and the older settings-only enable API remains compatible. Only the team lead or an admin on the host device can change host settings.
2. **Group routing.** Team work is sent through the ordinary multi-agent session. The session's group mode routes untagged requests; an authenticated member-device message follows that same routing, and explicit mentions target the mentioned group members.
3. **Full @mentions across devices.** `@handle` of any consented group member, local or remote, starts that member. Remote runs execute on the owner's device.
4. **Consent instead of per-request approval.** When joining (or later from settings), a teammate chooses which of their agents to contribute and accepts `TEAM_CONSENT_DISCLAIMER`: the lead/admins get sandboxed access to those agents. Consent records the accepted permission level, settings version and disclaimer version. If the lead raises the level (supervised → full-access) or the disclaimer version changes, consent becomes `needs-reconsent` and the owner device rejects new deliveries until the owner re-accepts. Owners can pause or revoke at any time from their own device; this is always honoured locally.
5. **Sandboxed permanent worker branch.** Remote-requested runs use one persistent isolated worktree per shared project and owner-side agent, on the stable branch `mingle/<handle-slug>/work`. The worktree retains earlier turns and commits; each turn records its own base so assignment scope checks apply only to that turn. At turn start Mingle merges the host-supplied integration commit when it is available and the worker worktree is clean. At successful completion Mingle commits remaining eligible in-scope changes and normally pushes the stable worker branch to origin with that owner's Git credentials. Workers may push their own branch directly, but never another branch, a default branch, or with force; Mingle never pushes tags, and credentials never leave the owner device. P2P artifact transfer remains the fallback when branch publication fails or no usable origin exists.
6. **Approvals.** In supervised mode a remote run's approval requests are shown on the owner device (existing UI) and mirrored to the host, where the lead/admin may decide. First decision wins; the owner can always deny. In full access, the host automatically approves native requests only while the current team setting and that agent owner's granted consent both permit full access; the owner device remains the runtime and permission boundary.
7. **Review and integration.** The host fetches each reported worker turn into a delivery-specific review ref under `refs/mingle/team/review/...` and updates the normal `origin/mingle/<handle-slug>/work` tracking ref. The reported `baseCommitSha` bounds assignment-scope validation to that turn; protected-path checks cover only commits not already contained in the current integration HEAD. The orchestrator reviews the exact reported commit and applicable project checks before integration. In Full access, an assigned task in Review can be accepted with `team_accept`; Mingle records `acceptedBy: 'orchestrator'` and performs a local merge, including a non-fast-forward merge when branches diverge. Merge conflicts abort and return a 409 asking the orchestrator to resolve them manually. In Supervised, acceptance remains a human decision. Dirty integration worktrees remain untouched.
8. **Integration publication.** After a successful Full-access `team_accept`, Mingle pushes the integration worktree's current branch to origin with a normal non-force, no-tags push. The default branch is permitted because the lead explicitly selected Full access; origin safety checks still reject mirrors, embedded credentials and ambiguous destinations. Mingle records push failures without undoing the local merge, and returns the failure to the orchestrator in the tool result and group status. After a successful push, Mingle sends each remote worker a durable no-wake team message with the branch and commit; the owner's device merges the clean integration update at the start of that worker's next turn. For manual integration merges not performed by `team_accept`, the Full-access orchestrator pushes normally and sends the equivalent no-wake notice itself. Supervised orchestrators ask the human before pushing. An orchestrator never pushes to a worker branch. While a worker is still running, the orchestrator yields instead of checking origin; Mingle wakes it when the branch is ready or publication fails.
9. **Leader handover and self-healing.** In Full access, quota/rate-limit, authentication, provider-unavailable and exhausted bounded-retry failures can trigger an automatic handoff. A configured fallback is preferred; otherwise Mingle selects an available low-load member, requiring valid current Full-access consent and an online owner device for remote agents. The change is recorded in `leaderHistory` (including the provider failure kind when applicable) and the group transcript. If no usable coordinator exists, the group pauses and `needsLeader` is true until a human picks one in Team structure. Worker assignments also carry a bounded failure note and committed-work reference to a replacement, with at most two automatic fallback moves per task. Quota/rate-limit cooldowns last until a reported reset or 15 minutes by default. A run without provider, tool or team-heartbeat activity for 10 minutes is stalled: Full access interrupts it, retries once on the same agent, then considers fallback; supervised teams keep the run for human recovery. Approval and question waits are not stalls. When the original leader returns it stays where the lead put it (worker or idle) until the lead promotes it again (`restored`).
10. **Interactive structure.** A new **Team structure** item in the project sidebar menu (next to Tasks, Activity, Agent map) shows an interactive tree: orchestrator at the top, workers below, an idle bench, fallback ranks, device/owner badges and live states. Lead/admin on the host can drag an agent onto the leader slot to promote/swap, drag to the bench to idle, reorder fallbacks, and remove agents. Others see it read-only.
11. **Agent's own conversation.** Clicking an agent in the floating presence bubble opens a drawer with that agent's own conversation (`GET .../team-agents/:agentId/activity`): requests it received, its replies, tool summaries, approvals, artifacts, errors. Remote agents are mirrored from `teamgroup.activity` updates sent by the owner device.

Assignment planning follows the same scoped routing as local groups. `team_members` reports each agent's provider/model/effort, owner-device location, queue/running load, health and active scopes. `team_assign` may use `recipient: "auto"` to prefer an existing scope owner, then lower load, health and provider diversity; its result reports the selected handle and reason. Overlapping scopes owned by different members are rejected through queued, running and Review states, including across remote worktrees; a dependency-ordered consumer may reuse a scope only after the producer delivery has completed, with normal task/artifact dependencies gating its start. A failed task's scope follows its assignment to the replacement.

## Architecture

- **Host device** = the device bound to the team lead account that owns the shared project binding. Once a teammate agent is added, the host uses that ordinary `ConversationGroup` as the team session and `mingle_team_host_projects.group_id` points to it; an empty group ID means settings are enabled but no team session exists yet. A converted single session defaults to `orchestrated` with its current agent as orchestrator. Remote agents are represented on the host by **proxy sessions**: local `Session` rows marked as team proxies (table `mingle_team_proxy_sessions`), so the existing group scheduler, handoffs, result card and Team MCP tools work unchanged.
- **Runtime seam.** When the group scheduler calls `runtime.start(sessionId, …)` for a proxy session, the host sends `teamgroup.delivery` to the owner device instead of starting a provider. `teamgroup.delivery.status` updates feed the proxy session's messages/run state and finally `groups.onRunFinished(sessionId, runId, outcome)`. Interrupts send `teamgroup.interrupt`.
- **Owner device executor.** Validates the delivery (sender is the host device of that team, sender account is lead/admin, consent `granted` for that agent, permission level ≤ consented, settings version not older than consent), maps `agentId` → local session, reuses that agent's persistent `mingle/<handle-slug>/work` worktree, merges an available clean integration update, starts the run with the group permission level, streams `teamgroup.activity`, forwards approvals, proxies Team MCP tool calls to the host as `teamgroup.tool.call`, pushes the worker branch at turn end, and posts its final status. Committed-artifact transfer is retained as the fallback when branch push fails.
- **Restart continuation.** After Full-access host restart, interrupted local deliveries receive one queued continuation after provider discovery. For remote deliveries, the host interrupts the stale owner turn before dispatching the fresh continuation to the same agent; the persistent owner worktree retains partial work. Supervised/balanced groups stay paused for explicit recovery.
- **Shared transcript.** Existing signed team-chat messages mirror the team session transcript for member devices. Human messages typed in the host group and local group-agent final replies are signed and fanned out after local acceptance. Remote final replies are posted by the owner's device. An authenticated member-device message is routed into the host group like a group-composer message; group client IDs prevent routing retries from duplicating work.
- **Structure broadcast.** The host broadcasts `teamgroup.structure` after each change so every member device can serve `GET /team-structure` read-only.
- Transport latency: after sending any `teamgroup.*` envelope, request an immediate transport sync instead of waiting for the periodic loop.

## Artifact transfer

`GitSyncService.exportTeamArtifact` packages a committed revision from the owner-selected shared repository and queues a `git.team-artifact.offer` plus encrypted `git.team-artifact.chunk` messages to the delivery's `integrationDeviceId`. Receivers enforce the existing 16 MiB bundle ceiling, 128 KiB chunks (at most 128), canonical base64, aggregate SHA-256, `git bundle verify`, and an exact advertised revision. Because the sender cannot establish the receiver's object ancestry before dispatch, artifact bundles currently include all history reachable from the selected commit; the optional base revision is validated as metadata but is not used to make a potentially incomplete bundle. A bundle too large to transfer fails rather than splitting into an unbounded set of transfers.

The receiver imports only the claimed commit into a deterministic ref under `refs/mingle/team/`, with project/delivery identifiers sanitized and collision-resistant. For completed worker branches, the host fetches the permanent `mingle/<handle-slug>/work` branch into a delivery-specific `refs/mingle/team/review/...` ref, pinning the exact reported turn commit even if a later turn has advanced the remote branch. It also updates the ordinary `refs/remotes/origin/...` tracking ref. An accepted result merges into the local team-session integration branch under the repository mutation lease, without checking out into an unrelated branch; the workspace must be clean. Diverged branches use a real merge commit, and conflicts abort without changing the integration branch. A successful Full-access acceptance then pushes the integration branch normally with no tags; a rejected push leaves the local merge and accepted task intact and is reported to the orchestrator. Duplicate imports of the same transfer are idempotent. Team output transfers require a still-active peer link, a matching durable delivery, the producing owner's device, active roster membership and current consent. On an owner device, input transfer offers may arrive immediately before `teamgroup.delivery`; the receiver first validates the active host and local consent, then rechecks the exact delivery and integration device before import.

The host records imported worker refs and exposes them to the orchestrator for review. A Full-access orchestrator can use `team_accept` only with a verification summary; acceptance records are shown in the result, the worker branch is merged locally under the repository mutation lease, and Mingle pushes the integration branch normally. Supervised tasks remain for human acceptance and pushing requires human approval. Successfully integrated runs receive a saved changed-file summary, so the group transcript and result card show remote worker paths like local worker paths. Imported refs remain available for review. For remote runs, committed handoff inputs are exported to the owner device, listed in `inputArtifacts`, and named in the run prompt before provider execution. Artifact transfer does not validate behavior. Team consent authorizes worker-branch publication, transfer and local integration; it does not change the separate approvals required by ordinary user-requested Git handoffs.

During an active remote assignment, `team_artifact` first validates the owner-side run, committed path, revision, task and authoritative assignment scope. The owner exports that exact commit to the host; the host imports it into an isolated team ref before recording the existing typed group handoff. This makes committed files available to the handoff verifier without fast-forwarding the group anchor while the owner provider is still running. Terminal completion remains responsible for integration after the run ends.

The host saves its own task, scope and base revision at dispatch. Before publishing a remote handoff or integrating terminal output, it checks every changed path in the base-to-result history, including intermediate commits, renames and deletions. Scope checks preserve Git path casing. A peer's declaration of one allowed file does not authorize additional changes in its commit.

Artifact operations recheck cancellation and delivery authority after asynchronous preparation, transport and import work. An interrupted MCP transfer removes unpublished transfer chunks and refs; a previously published group handoff remains available. Terminal imports use the recorded durable completion intent rather than requiring the provider to remain running. A later assignment can consume a remote artifact through its exact verified imported transfer and published handoff, without weakening the ordinary producing-worktree ancestry rule or changing the human checkout.

Remote completion replies are signed by the owner device and use a stable delivery ID. The host records request completion and integration without impersonating the remote agent. Normal terminal delivery, restart and duplicate requests recover the owner's signed reply from the saved final result, including a crash before the first reply was persisted. Recovery checks the current account, registered device, local project, agent/session and integration host. Temporary reply-signing failure does not block terminal status delivery. Separate deliveries answering the same human request retain separate identities.

| Method & path | Device | Who |
| --- | --- | --- |
| `POST /api/projects/:projectId/team-orchestration/share-session` | host | lead/admin |
| `POST /api/projects/:projectId/team-orchestration/enable` | host | lead/admin |
| `PATCH /api/projects/:projectId/team-orchestration` | host | lead/admin |

Errors use the standard `{error}` body; version conflicts return 409.

## Limits

Host offline ⇒ no new team work is scheduled (members see the host as offline). Max 64 agents per team project, 4 fallbacks, 8 contributed agents per device. Activity mirrors keep the latest 500 entries per agent. Team delivery payloads carry at most 30 artifact references; each artifact bundle is at most 16 MiB.

## Implementation notes

The host-side service is `apps/server/src/team-orchestration/host/service.ts`; `apps/server/src/team-orchestration/index.ts` constructs it and composes an optional owner-device side. Migration 20 creates `mingle_team_host_projects`, `mingle_team_host_roster`, `mingle_team_host_consents`, `mingle_team_host_deliveries`, `mingle_team_host_approvals`, and `mingle_team_proxy_sessions`. The settings/history and delivery/approval rows stay local to the host. Proxy sessions are ordinary local `sessions` rows with a separate owner/device mapping; they use the bound project path only as their local metadata workspace, and the host never launches a provider for them.

The host REST routes implement `POST .../team-orchestration/enable`, `PATCH .../team-orchestration`, `GET .../team-structure`, and `POST .../team-structure/changes`. Enable and edits resolve the verified collaboration roster, require an active lead/admin, and require the current device to match the source binding's leader device. Settings and structure writes use `expectedVersion`, return 409 when stale, increment the version on success, and broadcast a schema-validated `teamgroup.structure` to mutually linked active devices followed by immediate transport sync. Structure edits update the scheduler roster without starting inference; an explicit leader handover may resume retained planner work.

The proxy runtime seam records the host run/user message and sends a validated `teamgroup.delivery` containing the group-generated prompt plus group instructions, role, group/request/delivery IDs, permission level, settings version and host integration device ID. Authenticated `teamgroup.delivery.status` updates map to host session/run state; completion appends scrubbed assistant text and calls `groups.onRunFinished`. Host-side approvals appear in the existing approvals list and decisions return as `teamgroup.approval.decision`. Tool calls are validated and executed through the run-bound Team MCP bridge. Owners send a lightweight delivery heartbeat every 15 seconds while a run is active, including during approval waits. Owner status, heartbeat, activity, approval and tool-call messages extend the persisted 90-second idle deadline without emitting a user-visible state event; a configurable two-hour absolute cap bounds runaway work. The host re-arms persisted deadlines after restart. Timeout messaging reflects the device's actual transport presence, and a late completion can recover a delivery that only failed due to an idle timeout.

Quota-exhausted/offline leader handover walks the configured fallback order, requiring a current grant, online owner device and no recorded quota/rate-limit cooldown. Full-access recovery may select an eligible team member when the configured list is empty or exhausted. A successful change is added to leader history and retained work is redirected through the existing scheduler. If no fallback qualifies, the group pauses, `needsLeader` is broadcast and a signed team-chat status is posted. A returning leader is not automatically restored.

`TeamChatService` retains the existing REST surface for member-device composers and the signed mailbox. Member messages are routed asynchronously into the active host group; the old team-chat local-mention runtime path is removed. Host group messages and local final replies mirror through the signed transcript with source-identity deduplication. Remote agent replies remain signed and published by the owner device. Host changes to remotely authored human-message run state use a separate device-authenticated `teamchat.run-state` envelope accepted only from the bound project host; the original message signature and author remain unchanged. History requests can include up to 100 unique pending human-message IDs from that project, so an older queued/running row can recover its signed terminal state even when newer replies have advanced incremental history. Applying this repair never redispatches provider work.

The owner-side factory is injected through `TeamOrchestrationDeviceSideFactory` in `team-orchestration/types.ts`; its expected shape is `createDeviceSide({store, runtime, hub, transport, account, distributed, collaboration, teamChat, changed}) -> {routes(add), close(), latestStructure(sharedProjectId), localConsent(sharedProjectId)}`. The app accepts this factory optionally so the host runs without it. When absent, host routes and local orchestration remain available, but owner-side delivery execution/consent routes and non-host structure caching are not provided. The owner executor imports delivery inputs before starting, reuses the agent's permanent worktree/branch, pulls a clean available integration update, commits remaining scoped changes and pushes `mingle/<handle-slug>/work` normally. It reports branch push failures and uses P2P artifact transfer as a fallback. The host pins each completion's reported commit in `refs/mingle/team/review/...` for orchestrator review and updates the normal origin-tracking ref; Full-access `team_accept` records verification, merges locally, and pushes the integration branch normally. A successful push produces a no-wake message to remote workers; the owner merges the update at the beginning of its next turn. Push failures are returned to the orchestrator and recorded while keeping the local merge. Supervised teams keep human acceptance and ask the human before pushing.

Remote completion is a durable host-side intent: the host keeps the proxy delivery live while it fetches and records worker review refs, persisting progress so a duplicate terminal status or host restart resumes that work without replaying provider inference. The orchestrator reviews the fetched commit and, in Full access, can accept through `team_accept` with verification evidence; local merge requires a clean workspace and preserves diverged history. When restart recovery has queued a full-access continuation, the host sends `teamgroup.interrupt` to the old owner delivery and holds the proxy slot until that turn is interrupted or times out, then dispatches the fresh continuation to the same agent. The host records the final proxy message/run and notifies the group scheduler after review refs and terminal state settle. A durable delivery-deduplicated result wake also notifies the orchestrator when a remote worker's non-assignment request/message completes with a fetched branch or push failure. A worker's reply-requesting message after its assigned task reaches Review remains queued until its proxy delivery completes; genuine questions during active work can still wake their recipient, and informational messages do not.

Assignment deliveries carry the exact `scope` saved on the matching group assignment (`deliveryId` lookup). The owner executor uses this host-validated path list to limit committed outputs; it never infers scope from prompt prose.

Workers execute the current assignment directly. The original human request embedded in an assignment is quoted background; coordinator-directed delegation instructions are not transferred as worker authority. A reply-requesting clarification is a message delivery, not a continuation of task authority: workers answer it with `team_message`, and request a new scoped assignment when implementation or task status must continue on another turn.

`TeamStructurePayloadSchema` carries optional `host` identity, per-member `consent` fields and `teamSession` so a validated broadcast can populate the read-only structure/session view on another device. Existing required payload fields and message names remain unchanged.
