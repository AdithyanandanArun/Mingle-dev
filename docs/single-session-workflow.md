# Autonomous single-session work (implementation interface)

A standalone root session can explicitly start a bounded goal. Permissions remain the selected native provider policy; autonomous follow-through never changes provider, model, effort, permission level or worktree. The agent uses its existing conversation, progress checklist, tools and project memory. Human input, failed/uncertain dispatches, explicit pause/stop and exhausted limits remain visible boundaries.

Contracts live in `packages/contracts/src/session-workflow.ts`. `Bootstrap.workflows` is optional for compatibility. Each snapshot holds a unique workflow id, version, session/task ids, goal, running/paused/stopped/completed state, reason/summary, limits and counters, pinned configuration, current/last run ids and a persisted deadline. The default is eight total turns, four hours and two no-progress continuations. Explicit resume may grant more turns/time within the hard contract limits.

Local, existing Host/Origin-guarded routes:

- `GET /api/sessions/:id/workflow` → `{ workflow: SessionWorkflow | null }`.
- `POST /api/sessions/:id/workflow` → `SessionWorkflow`; body is `StartSessionWorkflowSchema` (goal, optional limits, attachments and context references). Reuses the native runtime and attachment path; rejects active/busy, grouped, child, proxy, archived and unsupported sessions.
- `POST .../workflow/pause` and `POST .../workflow/stop` → `SessionWorkflow`; require `{ expectedVersion }`.
- `POST .../workflow/resume` → `SessionWorkflow`; requires `{ expectedVersion, additionalTurns?, extendMinutes? }`. Check the snapshot version, current eligibility/configuration and runtime lock before starting.

A run-scoped `mingle_workflow_finish` tool is exposed through the existing progress MCP connection only for an active workflow invocation. It accepts `{ outcome: 'complete'|'blocked'|'needs_human', summary }`, derives its workflow/session/run identity on the server, and records a pending report. Applying a successful completion waits for the native turn to end. It is an agent-reported result, not an independent certification of checks, integration or publication. The goal task remains in Review; ordinary task acceptance is unchanged.

The service owns durable workflow/run bindings and schedules continuations at a runtime idle edge after provider cleanup and queued-input handling. It does not infer success from assistant prose or a native turn ending. Unreported outcomes receive one bounded verification turn; repeated missing reports, repeated no-progress turns, denied approvals, unanswered questions, provider refusal/failure, configuration changes and budget exhaustion pause with a useful reason. In-flight subagent results are awaited without polling; user-queued input has priority. Pause/Stop must also fence late subagent wakeups and stale continuation callbacks. Explicit human sends remain possible.

Restart preserves the goal and history, pauses the workflow, and requires explicit Resume after inspecting partial work. `SessionResumeService` must skip workflow-owned runs, avoiding a second automatic recovery owner. Native permissions, approvals and context-compaction rules stay intact. No automatic retry of failures with uncertain side effects is added.

Intended service seam for parent integration: constructor options `{ store, runtime, tasks, recovery, groups }`; methods `get(sessionId)`, `list()`, `start(sessionId, parsedInput)`, `pause(sessionId, expectedVersion)`, `stop(sessionId, expectedVersion)`, `resume(sessionId, parsedInput)`, `ownsRun(runId)`, `close()`. Service/runtime may add explicit internal hooks; no public request can supply a run binding. The parent owns app/routes wiring and the Composer UI. All provider tests must use fake adapters and disposable data.

## Server implementation (`apps/server/src/session-workflow/`)

**Wiring.** `new SessionWorkflowService({ store, runtime, tasks, recovery, groups, log })` after the runtime, progress MCP bridge, groups and recovery exist. The constructor creates its tables (`session_workflows`, `session_workflow_runs`; no foreign keys), pauses any row left `running` by a crash (`app-closed`) and installs the runtime hooks (`runtime.setWorkflowHooks`). Pass the service as the optional sixth argument of `SessionResumeService` (`{ ownsRun }`); call `close()` before `runtime.shutdown()`. Extra helpers: `isRunning(sessionId)`, `stopActive(sessionId)` (stop without a version check before a native interrupt), and `workflowOwnsRun(db, runId)` / `WORKFLOW_RESTART_MESSAGE` in `ownership.ts` for startup recovery text that runs before the service exists. All methods are synchronous and throw `HttpError` (400/404/409).

**Start** runs in one transaction: goal task (`ready`), workflow row, and `runtime.start` with `taskId`, `deferContextResolution`, attachments and context references. A refused start rolls back the task, row, run, user message and attachment claims. The visible first message is the original goal (`kind: workflow-start`); the provider prompt carries the budget and rules. Automatic turns use `workflow-continuation`, `workflow-verification` and `workflow-resume` message kinds with short audit text. Every turn reuses the original `taskId`, so project intelligence never creates a per-turn request task.

**Runtime seam** (`SessionWorkflowHooks`, `session-workflow/hooks.ts`): `prepareStart` may adopt a human, queued or subagent-result start as a goal turn; `runBound` runs inside the transaction that inserts the run row (budget freeze); `recordReport` backs `mingle_workflow_finish`; `runEnded` is synchronous right after the run is finalised and records the outcome; `idle` fires once per run **after** provider cleanup (including the provider-ignored-abort path) **and** after the queue-drain attempt, and is the only place follow-up work is scheduled (through one fenced microtask); `allowQueuedStart` lets the drain skip fenced items. `RunEndInfo` carries run id, outcome, redacted failure, classification, boundary counters (approvals denied/expired/cancelled, questions answered/cancelled), changed-file count, tool count and the final checklist.

**Decisions after a native completed turn** (never inferred from prose): applied report (`complete` completes, `blocked`/`needs_human` pause); denied/expired approval or cancelled question pauses and wins over a report; config drift pauses; turn or time budget pauses; in-flight subagents mean wait (no polling, no turn spent); no open checklist and no report means one verification turn, then `unreported-outcome`; an open checklist continues while files change or the checklist moves, and pauses `stalled` after `maxStalls` consecutive no-progress turns. Failed, refused, quota and interrupted turns pause with a reason and are never retried; a report from such a turn is discarded.

**Concurrency.** One deadline timer per running workflow (no polling). Pause/Stop/deadline persist the new state, bump a fence, clear the timer, mark the run detached and then interrupt, so stale continuation callbacks and late results see a non-running workflow. `expectedVersion` is strict; passive run clean-up after a pause does not bump the version. Late subagent results queued after Pause/Stop are detected by the `Subagent @name ` prefix plus a delegated-subagent row that started before the pause/stop; they stay queued until Resume or an explicit send. A human send between turns or from the queue is adopted as a goal turn (it resets the stall counter and is counted in the budget).

**Resume** re-pins the current session configuration, may grant `additionalTurns` (hard 50) and `extendMinutes` (hard 24 hours from creation), resets stalls, and starts a turn whose prompt tells the agent to inspect the worktree and avoid repeating side effects.

**Adapter scope.** The progress allowlists of the Claude, OpenCode and Antigravity adapters include `mingle_workflow_finish` (Codex already approves the whole progress server). OpenCode/Antigravity ACP `stopReason: refusal` now fails the run with code `refusal` instead of completing; `turn_limit` classifies as `output_truncated`. `ProviderFailure.kind` is frozen, so refusal is carried in `providerCode`.

**Known limits.** The agent's report is not independently verified. Wall-clock deadlines include paused time. Queued messages present at Resume are delivered after the resume turn. Subagent wakeups are recognised by message shape because `delegated-subagents.ts` is not changed.
