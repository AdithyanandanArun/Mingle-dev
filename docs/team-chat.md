# Team chat

Team chat remains a durable, signed REST/mailbox transcript for member devices, but it is not a separate team-work surface. When the shared project has a team session, member-device messages are routed into the host's ordinary multi-agent group and the same transcript mirrors that session's human messages and agent replies.

## What it does

- **Project binding:** `GET /api/projects/:projectId/team-chat` requires the local project to be bound to a shared project. The response includes paginated messages, active teammates, published local and remote agents, and the actual transport/device status.
- **Human messages:** `POST /api/projects/:projectId/team-chat/messages` validates the body and roster mentions, signs and stores the message locally, then returns without waiting for transport. Encrypted fan-out and host group routing happen in the background. Message IDs make retries and duplicate mailbox delivery idempotent. Ordering is `createdAt`, then ID.
- **Backfill:** Opening an empty or previously opened chat sends `teamchat.sync.request` with the latest timestamp (or `null`) to mutually linked peers. Replies are accepted only for a live request from that exact peer device, expire after two minutes, carry bounded batch indices/counts, and contain at most 200 messages and 180 KiB per batch. Requests are limited to one per peer/project every 30 seconds; responses are bounded to 200 batches per peer per two-minute window. Backfill includes only messages with valid author-device provenance; repeated delivery is deduplicated locally.
- **Session history:** The chat's **Share this session's history** control imports the latest 200 durable user/assistant messages from one local session. The existing credential scrubber runs before they enter the shared chat. Tool output, attachments, approvals, system messages and hidden reasoning are not imported. Per-session/message source IDs prevent duplicate imports. A session appears as an agent only when it is currently published in the shared-project roster; otherwise both roles are attributed to the importing human account. Each imported record is sent as a provenance-signed message from the importing device.
- **Team session routing:** On the host, an authenticated member-device message with `@mentions` targets those group members; an untagged message follows the group's normal mode. Team-chat itself does not start provider sessions. The group scheduler and owner-device proxy executor retain consent, group permission and approval enforcement.
- **Transcript mirror:** Host group-composer messages and local agents' final replies enter the signed transcript after local acceptance. Remote agents publish replies from their owner device. Source-session/message identities make retries idempotent and prevent incoming team-chat messages from being mirrored back as new human messages.

The sidebar link appears only when the server reports a shared-project binding. `openTeamChat(projectId)` is also exposed by the web store so the join flow can open the conversation after enrollment.

## Trust and delivery

Transport authenticates and decrypts the mailbox envelope and checks the current device registration and mutual fingerprint links. Team chat independently parses every `teamchat.*` payload with strict Zod schemas, verifies the sender device and active account membership, checks the team/shared-project relationship and local binding, and validates authors before persisting. Each message's immutable identity/content fields are signed with the author's registered device Ed25519 signing key; the signed canonical record binds the message ID, team/project IDs, author identity, body, mentions, reply target, timestamp, import source, and author device ID. The receiver looks up that device's registered public key, checks its active team membership/non-revoked status and account ownership, and verifies the signature. Direct messages must be from the authoring device. Backfill may relay another member's message, but its original authoring device must still be registered, active and verifiable. Unknown, invalid, or revoked author devices are rejected (not stored as “unverified”); therefore history created before provenance support, and history from subsequently revoked devices, remains visible only on devices that already stored it and is not redistributed. Human display names are resolved from active membership data; agent names, provider and model are resolved from the currently published shared-project roster. Peer-supplied author labels are never trusted. The remote sender cannot choose a local project path or start another device's provider session.

SQLite is the local durable history. `sending`, `sent` and `failed` describe the local view of delivery. `sent` means Mingle durably accepted the encrypted envelope into its local outbox; it does **not** mean the cloud relay accepted it, the peer opened the chat, or an agent ran. The HTTP send response may initially say `sending`; the local delivery state is updated after background fan-out. The composer and connection banner show the transport's current status and mutual-link counts. If delivery fails, the local message remains visible and retry/backfill can reconcile later.

Message text and author metadata are shared only with devices whose owners are active team members and whose device fingerprints are mutually linked. Teammate display names and all message text are data, not instructions. Agent context is length-bounded and labelled untrusted. Human text, imported session text and agent replies pass through Mingle's existing best-effort credential scrubber before persistence or sharing.

## Limits and verification

- Message bodies are limited to 20,000 characters and mentions to 20 agents. Each shared project retains at most 10,000 messages locally, pruning the oldest records first.
- REST pages contain up to 200 messages. Backfill returns the latest applicable bounded batch; older history can be imported explicitly from a local session.
- A history import is capped at 200 durable user/assistant messages and exposes whether earlier messages were omitted.
- A project without a team session can retain and synchronize team-chat messages, but team-chat messages do not start local or remote agent runs on their own.
- Group delivery, remote approvals and agent results remain ordinary group-session behavior; the transcript does not bypass or replace those controls.
- SQLite migration 19 creates the local message table, import-deduplication index, and author device/signature columns. Provenance column reconciliation is idempotent for databases that opened the initial unreleased migration 19. Team chat uses the existing distributed-team cloud tables; it adds no cloud transcript table.

Focused tests exercise signed fan-out, duplicate handling, membership rejection, backfill bounds, HTTP history import, group routing, and two-app encrypted mailbox delivery. No paid model inference is used by those tests.
